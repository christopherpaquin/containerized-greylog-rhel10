## 2026-10-01 20:29
**Task:** Fix 2 from the readiness review - TLS for the web UI/API (user chose Graylog-native TLS with a generated self-signed cert, "good for 10 years"), plus, added mid-task by the user, TLS syslog that is optional and toggled in .env.
**Decision:** Web UI/API is HTTPS-only on 9000 using a cert/key generated once by deploy.sh (RSA-4096, `GRAYLOG_TLS_CERT_DAYS=3650`, never rotated on rerun) in `${DATA_ROOT}/tls`, mounted `:ro,Z`. A JVM trust store (image cacerts + our cert) is built by running keytool from the pinned Graylog image with no network/volume, and the `-Djavax.net.ssl.trustStore` flags live in the Quadlet template, not .env. `GRAYLOG_HTTP_PUBLISH_URI` is pinned to `https://<container name>:9000/`. Syslog TLS is `SYSLOG_TLS_ENABLED` (default false) + `SYSLOG_TLS_PORT` (6514): a third input reusing the same cert; plaintext 1514 always stays. Added an explicit image pull step. Also fixed two older manifest bugs the reviewer raised (package manifest written to cwd; uninstall deleting it before reporting).
**Why:** Graylog proxies cluster API calls to its own publish URI using the default JVM trust store, so a self-signed cert without a trust store breaks node/cluster pages - hence the trust store and a publish URI whose host is a SAN. Keytool-in-image avoids needing Java on the host and keeps the image's public CAs. The cert is never auto-rotated (clients pin it), so deploy dies rather than warns if the external URI host is not a SAN or the key doesn't match. TLS-syslog mismatches (asked for but not TLS, or disabled but still present) are fatal in deploy and a FAIL in healthcheck, because the input API fields (`tls_cert_file`, `tls_key_file`, `tls_client_auth`) could not be confirmed against a running Graylog 7.1 - the code reads the input back and checks `attributes.tls_enable` instead of trusting the payload. The TLS firewall port we open is tracked in its own manifest file so a port change or disable closes exactly what we opened, and fails closed if firewalld can't.
**Progress:** Implemented; 105 unit tests pass locally, shellcheck has no new error-level findings. NOT validated on a live RHEL 10 VM - none available this session; nothing here (Graylog TLS startup, keytool path in the image, trust store, SELinux on the ro mount, input API schema) has run for real. ## 2026-10-01 20:34
**Task:** Fix 3 - firewall (user chose option B: fix zone handling and rule ownership, plus an allowed-sources list in .env).
**Decision:** step_firewall is now a reconcile loop over "entries" (`<zone>|port|<p>` or `<zone>|rich|<rule>`): desired set is computed from ports + `FIREWALL_ALLOWED_SOURCES`; rules we added are recorded in `${DATA_ROOT}/.manifest.firewall_rules`; owned-but-unwanted rules are removed (fail closed, verified gone), missing ones added, pre-existing ones left alone and not recorded. Zone = `FIREWALL_ZONE` or the zone of the default-route interface, falling back to the default zone. Trusted-zone bridge binding is recorded only when deploy made it, and uninstall removes only a recorded one.
**Why:** One mechanism covers source-list changes, zone changes, port changes and the TLS-syslog toggle, replacing the separate TLS-port tracking file from fix 2. Plain `firewall-cmd --add-port` hits the default zone, which is not necessarily where the NIC is. With sources set, a pre-existing plain port rule we don't own would silently defeat the restriction, so deploy warns and prints the removal command rather than deleting an admin's rule. Legacy `.manifest.firewall_ports_added` lines are adopted as default-zone port entries so upgrades reconcile. Known gap: a deployment made before this change has no trusted-iface record, so its uninstall now leaves that binding behind (harmless, stale interface name).
**Progress:** Implemented, 113 unit tests pass (stateful firewall-cmd stub). Not yet run against real firewalld.
